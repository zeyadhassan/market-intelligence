The host has four NVIDIA **H200-141C vGPU** slices (144,384 MiB each, 564 GiB total). Any attempt to run a model across more than one slice — tensor parallelism — fails during NCCL initialisation, before any model weights are loaded.

I have good news, and it changes your capacity conclusion.
This is not a CUDA IPC restriction. It is a missing VM configuration setting, and the 423 GiB you are preparing to write off is very likely not lost.
The error points near init.cc:491 in NCCL 2.28.9, inside the function commAlloc(). In the v2.28.9-1 source, the block reads:

props.handleTypes = cudaMemHandleTypeNone;               // line 491
...
CUDACHECK(cudaMemPoolCreate(&comm->memPool, &props));    // line 493
This is the CUDA stream-ordered memory pool allocator, not the CUDA IPC memory-handle exchange. Two details in the surrounding code confirm it:
• The pool is created with props.handleTypes = cudaMemHandleTypeNone — explicitly without an exportable IPC handle. This call cannot fail on an IPC restriction. • It sits in commAlloc(), which is purely local communicator setup. It runs before NCCL selects a transport and before any rank contacts any other rank.
That second point explains the behaviour you found puzzling. NCCL_P2P_DISABLE=1, NCCL_SHM_DISABLE=1 and NCCL_CUMEM_ENABLE=0 had no effect because none of them gate this call — commAlloc contains no reads of those env vars, and NCCL_CUMEM_ENABLE specifically gates the separate cuMemCreate (VMM) path elsewhere in NCCL, not cudaMemPool*. It is also why the failure appears after NCCL reports "Using network Socket": the socket transport was selected successfully, and the failure is a separate, local CUDA capability check.
When the device reports that CUDA memory pools are unavailable, the CUDA runtime returns an unsupported-operation error (typically cudaErrorNotSupported, numeric code 801). The CUDA error string is generic and does not name the missing capability, which is why the message is so easy to misread.
For completeness: this call was introduced in NCCL 2.23 and is present in every release since. Changing NCCL version will not avoid it.
Why the capability is missing on your VM 
On NVIDIA vGPU, the CUDA memory-management path these pools depend on is gated behind Unified Virtual Memory (UVM), and UVM is disabled by default in a vGPU virtual machine. It must be enabled explicitly, once per attached vGPU, in the VM configuration.
This requirement is documented publicly, and you can verify it independently:
• NCCL troubleshooting guide, Unified Memory (UVM): https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting.html#unified-memory-uvm • NVIDIA AI Enterprise, vGPU UVM — known issues and limitations: https://docs.nvidia.com/ai-enterprise/release-8/latest/infra-software/vgpu/features/uvm.html
Without UVM, the CUDA memory-pool creation calls that NCCL 2.23 and later make unconditionally will fail, and NCCL has no fallback path — which produces exactly the unhandled CUDA error you are seeing.
We can confirm from your ESXi bug report that it is not currently enabled. The host log records, for all four vGPUs:

vmiop_log: (0x1): vGPU migration enabled
vmiop_log: (0x2): vGPU migration enabled
vmiop_log: (0x3): vGPU migration enabled
Enabling UVM disables vGPU migration capability. Migration still being enabled on all four therefore tells us the setting has not been applied.
